## 1. 가장 중요한 구조적 발견: “빈도”와 “비용”의 분리

베이스라인(L0)에서 **호출의 71%는 n=4**인데, **시간의 96%는 n=256**에서 소모된다.

| n | 호출 비율 | 시간 비율 | 평균 elapsed |
|---|-----------|-----------|--------------|
| 4 | 70.8% | 4.1% | 0.18 ms |
| 256 | 27.0% | 95.8% | 11.09 ms |

**인사이트:** SLAM 매처는 대부분 “싼 호출”(n=4)을 많이 하고, 가끔 “비싼 호출”(n=256, branch 확장)을 한다.  
→ 최적화 우선순위는 **평균 avg가 아니라 n=256 구간**이 맞고, Fig.3이 이를 한 장에 보여준다.

## 2. work_unit(n×p)당 비용 — 구현이 연산량을 제대로 반영하는지

동일 bag에서 **elapsed / (n×p)** 를 n별로 보면, level이 올라갈수록 **단위 연산당 시간이 단조 감소**한다.

| Level | n=4 (µs / work_unit) | n=256 (µs / work_unit) |
|-------|----------------------|------------------------|
| L0 | 42.49 | 40.33 |
| L2 | 28.34 | 25.60 |
| L6 | 22.74 | 7.25 (omp_cand) |
| L7 | 20.49 | **3.30** (cuda) |

**인사이트**

- L0→L2: n=4·256 **비슷한 비율**로 개선 → **루프 교환**은 n에 무관한 공통 이득(px/py 재사용).
- L2→L6 @ n=256: **25.6 → 7.25 µs/wu (3.5×)** — n=256에서만 **OpenMP 후보 병렬** 효과가 큼.
- L6→L7 @ n=256: **7.25 → 3.30 µs/wu (2.2×)** — 같은 n에서 GPU가 CPU OMP보다 유리.
- L7 @ n=4: L6과 거의 동일(20.5 vs 22.7 µs/wu) → **GPU를 쓰지 않는 설계가 데이터와 일치**.

## 3. “빨라지면 더 많이 호출한다” — SLAM 피드백 루프

| Level | calls | cumulative (ms) | cum/call (avg) |
|-------|-------|-----------------|----------------|
| L0 | 27,754 | 86,824 | 3.13 |
| L2 | 41,261 | 82,476 | 2.00 |
| L6 | 85,260 | 52,132 | 0.61 |
| L7 | 133,496 | 42,864 | 0.32 |

- L7은 L0 대비 **calls 4.81×**, 그런데 **총 score_all 시간은 2.03×만 감소**.
- opt2만 봐도: calls **1.49×** 증가, cumulative는 **약간 감소** (86824→82476).

**인사이트:** `score_all`을 빠르게 하면 **같은 bag 안에서 매칭 트리가 더 깊/자주 진행**되어 호출 수가 늘 수 있다.  
→ **avg ms/call만으로 “시스템 전체가 4.8배 빨라졌다”고 쓰면 안 됨.**  
→ **cumulative**와 **n=256 구간 평균**을 함께 써야 한다 (Fig.5).

`fast_matcher`는 `Score` → `Branch` 재귀로 후보를 확장하며 `score_all`을 반복 호출한다. 상위 로직은 수정하지 않았으므로, 이 피드백은 **순수하게 score_all 가속의 2차 효과**로 해석할 수 있다.

## 4. CPU ablation에서 놓치기 쉬운 점

### 4.1 LICM(L1)은 로그상 사실상 0%

n=256 평균 11.09 → 11.07 ms. **나눗셈 1회 제거**는 랜덤 grid 읽기 비용에 묻힘.

### 4.2 prefetch/branchless(L3~5)는 n=256에서 opt2보다 나쁨

- 원인 가설: LiDAR 맵핑 좌표가 **행 단위 순차 접근이 아님** → `__builtin_prefetch`가 잘못된 행을 끌어옴.
- opt4/5에서 **calls가 41k → 31k로 감소**하는데 cumulative는 비슷 → **호출당은 느려졌지만 매칭이 덜 진행**했을 가능성. (branch 단계 timing 변화·수렴 차이 — 추가 검증 여지)

### 4.3 L6에서 n=256의 일부(110회)가 `path=legacy` 없이 omp가 아닌 경로

전체의 0.1% 수준. dispatch 경계(n=64 threshold) 근처 또는 로그 태그 누락 run — 보고서 영향은 미미.

## 5. GPU(L7) 세부 인사이트

### 5.1 n=256 CUDA 지연 분포

- 호출 37,719회, **중앙값 0.827 ms**, p90 1.15 ms, **최대 96.3 ms (8건 >10 ms)**
- 96 ms급은 **첫 grid H2D + 컨텍스트 워밍업**으로 해석 (device 캐시 이후 대부분 ~0.9 ms).

### 5.2 L7에서 n=4가 cumulative의 19%를 쓰지만 호출의 70%

- GPU는 n=256에만 쓰여도, **“싼 호출”이 많아** 전체 avg를 0.32 ms까지 끌어내림.
- **GPU 이득을 말할 때는 반드시 n=256 cuda 구간**을 따로 인용 (Fig.2).

### 5.3 CPU OMP vs GPU @ n=256

| 경로 | mean elapsed (n=256) | µs / work_unit |
|------|----------------------|----------------|
| L6 omp_cand | 1.996 ms | 7.25 |
| L7 cuda (trim) | 0.908 ms | 3.30 |

**2.2× (시간/call), 2.2× (시간/work_unit)** — 거의 동일한 비율 → **후보 병렬화 축이 동일**할 때 GPU가 메모리 병렬성으로 이김.

## 6. 하드웨어·설계 관점 종합

| 구간 | 지배 연산 | CPU 최선 (L6) | GPU (L7) |
|------|-----------|---------------|----------|
| n=256 | 256×1081 random read | 4코어 OpenMP | 많은 CUDA 스레드 |
| n=4 | 4×1081, 호출 다수 | 전개 커널 n4 | CPU 유지 (전송 회피) |

**한 줄:** Jetson PA01에서는 **“어디를 최적화할지(n)”를 먼저 고르고**, 그다음 **그 n에 맞는 병렬 축(CPU 코어 vs GPU 스레드)** 을 고르는 것이 avg-only 최적화보다 훨씬 중요하다.

---

## 7. 보고서·다음 실험에 넣을 문장 (복붙용)

> 로그를 n별로 분해한 결과, score_all 시간의 96%는 n=256 호출(전체 호출의 27%)에서 발생하였다.  
> 루프 교환은 n=4·256 모두에서 work_unit당 비용을 낮추었고, OpenMP와 CUDA는 n=256에서만 추가로 3.5×·2.2× 개선하였다.  
> 최적화 후 동일 bag에서 score_all 호출 수는 최대 4.8배 증가하였으나 누적 시간은 2.0배 감소하여, 호출당 평균만으로 가속도를 보고하지 않고 cumulative와 n=256 구간을 병기하였다.
